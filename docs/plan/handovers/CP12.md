# Checkpoint 12 handover

- **Checkpoint:** CP12 — Organisation/enterprise + policy/risk
- **Status:** PASS (gate: `experiments/cp12/cp12_gate.sh`, live 8/8)

## What changed
- `internal/app/policy.go` — org/policy/risk/audit/fleet:
  - `orgs` collection (owner, members, repos), `policies` collection (rules),
    `audit` collection (every policy decision: allow/deny/escalate + actor +
    reason).
  - Policy engine evaluated at run choke points:
    - **agent**: `deny_paths` glob against the file a role writes
      (implementer/reviewer); denied runs fail with the policy reason.
    - **integrate**: `require_approval_risk` — integrations at/above the risk
      class are escalated (queue item blocked) for human approval instead of
      integrating.
    - **workflow**: `budget_steps` — a run whose budget exceeds the policy cap
      is denied.
  - `orgForRepo` resolves a repo to its owning org id (a repo with no org has
    no policy → the simple case is unconstrained).
  - **Risk model**: risk = blast_radius × uncertainty (files touched ×
    conflict/preview state) → low/medium/high; risk drives the integration
    policy gate.
  - API: `POST /api/orgs`, `POST /api/orgs/{id}/policies`,
    `GET /api/orgs/{id}/fleet` (org + repos + queue + workflow runs +
    escalations), `GET /api/audit`.

## Gate evidence (live, 8/8)
1. Org created owning the repo; policy `deny_paths: ["config/*"]` +
   `require_approval_risk: high` + `budget_steps: 100`.
2. An implementer workflow targeting `config/secrets.txt` **fails** with the
   policy reason; a workflow targeting `public.txt` completes.
3. The audit trail records both decisions (agent/deny + agent/allow).
4. A repo **without** an org/policy is unconstrained (config write completes) —
   the simple repo case is not broken.
5. A high-risk (10-file) integration is **blocked** by the policy gate
   (escalate for approval), risk=high.
6. A workflow with budget 200 exceeds the policy cap (100) → denied.
7. Fleet view lists org repos/queue/workflow runs/escalations.

## Security notes
Policy decisions are audited with actor + reason; the agent policy is enforced
at the shared run choke point (workflow + attempt paths). Risk escalation
routes to the existing Needs Attention / escalation surfaces (CP11).

## Impact on later checkpoints
- CP13 dogfooding: Switchyard's own org/policy can be enforced on itself.
- CP14 hardening: richer policy rules, per-role escalation, enterprise
  credentials + audit + fleet are post-v1 expansion points.

## Addendum (post-cp13 review) — wording accuracy

- **Risk model:** the conceptual model remains `blast radius × uncertainty`.
  The current implementation uses **v1/prototype signals**: file count /
  footprint, preview-conflict state, repository rules, and explicit policy.
  That proves risk-derived policy can alter autonomy; it does NOT claim the
  complete risk model is implemented. Future richer blast-radius signals
  (auth/security sensitivity, schema/data migration, external side effects,
  destructive operations, billing, production config, public API
  compatibility, privileges, reversibility) are not built now.
- **Organisation scope:** this checkpoint proves the **organisation/policy
  architecture** (org→repo grouping, policy, risk-based escalation, workflow
  budgets, auditing, fleet aggregation, unconstrained simple repo). It does NOT
  prove full enterprise authorization: membership role enforcement, per-repo
  permission matrices, enterprise SSO, organisation-secret lifecycle,
  compliance retention, or fleet-scale throughput — those are later
  hardening/expansion.
