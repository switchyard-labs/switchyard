# Checkpoint 9 handover

- **Checkpoint:** CP9 — Integration Queue full semantics
- **Status:** PASS (gate: `experiments/cp9/cp9_gate.sh`, live 8/8)

## What changed
- `internal/app/queue_integration.go` — the Integration Queue:
  - `iq` collection (id, pr_id, repo, base, branch, status, risk, policy,
    attempts, error, created_at[ms], updated_at).
  - `POST /api/prs/{id}/enqueue`, `GET /api/queue`, `POST /api/queue/{id}/requeue`.
  - Worker (`StartIntegrationQueue`) processes items in **strict FIFO** (one at
    a time; millisecond-created_at ordering). This is what guarantees
    ordering: a later PR that edits the same file previews against the earlier
    PR's integration, so conflicts are detected and routed to the repair loop
    instead of surfacing at merge time.
  - **Policy:** an item integrates only when its PR check passed AND preview
    integration is clean. Failing checks are rejected at enqueue (409);
    preview conflicts block the item with error findings and route the
    underlying attempt to `conflict` (uniform with the CP8 preview endpoint).
  - **Canonical-head freshness:** integration is CAS-guarded (MergeBranch);
    a moved base is re-queued (stale repair loop) with bounded attempts.
  - **Repair loop:** conflict → blocked → conflict-resolver resolves the
    source branch → requeue → preview clean → integrate → done.
  - **Risk classes:** low/medium/high from change scope (files touched).

## Gate evidence (live, 8/8)
1. Policy: failing-check PR cannot enqueue (409 check_not_passed).
2. Clean churn: 3 PRs integrate in FIFO order; canonical has all features.
3. Same-file contention: first PR integrates; second is **blocked** by preview
   conflict; conflict-resolver resolves it; requeue integrates it; canonical
   reflects the deterministic resolution.
4. Risk: 10-file PR classified `high`.
5. UI observability: queue states (queued/running/blocked/done + risk + policy)
   observable via `GET /api/queue`.
6. Performance: see below.

## Performance measurement (CP9, live)
| Scenario | Enqueue phase | Full queue→done | Per item |
| --- | --- | --- | --- |
| 3 clean PRs | — | 18–22 s | ~6–7 s |
| 10 clean PRs | ~10 s | 42 s | ~4.2 s |

Each integration does a scratch clone for preview + a scratch clone+push for
the merge (repeated full object transfer). At this scale that is acceptable,
but the data now **justifies the cached bare-mirror / worktree model** for
CP14/CP9-hardening: clone prep dominates. Recommendation: maintain a bare
mirror per repo and use `git fetch` + shared-object worktrees, cutting
per-integration latency and object transfer substantially. (Decision is
evidence-based, not aesthetic.)

## Security notes
Queue policy enforces check-pass + preview-clean before any canonical change;
integration is provenance-recorded (ref_updates: `queue:<id>:<pr>`). The
conflict-repair loop uses the role-scoped conflict-resolver substrate.
