# Cloudflare Actions architecture

Actions validate Git commits. Switchyard engineering workflows coordinate people and Agents. They are separate domains; Go never executes CI commands.

A native `cf.artifacts.repo.pushed` trigger starts the deployed `Actions` Workflow. The official `@cloudflare/ci` engine normalizes the event. The Worker verifies the namespace and repository allowlist, resolves the repository through its Artifacts binding, selects the owner-approved definition and binds the run to the pushed 40-character SHA and definition revision. Each job starts from that immutable checkout; subsequent steps use the official SDK's R2 snapshots. This installation runs jobs sequentially with one basic Container instance.

The Worker stores intent, state and bounded logs in R2. Switchyard uses a timestamped HMAC control protocol for definition approval, dispatch, status, discovery, cancellation and logs. Workflow instance IDs enforce one execution per dispatch ID; an ambiguous create retries the same ID, and conflicting payloads return 409. Native push IDs come from Cloudflare. The signed status read is the reporting boundary; C11 persists normalized coordination in Trestle. Polling is deliberate: the shared Linode currently has no HTTPS callback origin.

Definitions use JavaScript first: `.switchyard/actions/ci.js` exports `{refs, jobs}` and ordinary expressions can generate repeated steps. Approval compiles the module without host callbacks, filesystem, network or credentials, with a 64 KiB source bound, one-second interrupt and stack limit. The source hash becomes the revision. Only an authorized maintainer may approve definitions; arbitrary pushed configuration is not evaluated in the privileged Worker. This initial configuration API has explicit jobs/steps rather than impersonating the SDK's full programmable runner API. TypeScript transpilation, parallel lanes and cache controls are not implemented.

Each run has at most eight jobs, 32 total steps, 16 steps per job, 8 KiB commands and 120-second command timeouts. Worker request bodies stop reading at 128 KiB. Logs are captured after a step completes, with a 1 MiB bound per stdout/stderr and explicit truncation. Failure diagnostics follow the SDK's smaller tail limit. These are captured logs, not live process streaming. R2, account and control credentials remain Worker secrets; runner options disable Cloudflare and source-control credential injection. The official checkout still uses a repository-scoped read token for source retrieval; this is not a zero-credential checkout.

## Deployment

`workers/actions` pins the CI SDK 0.2.0, Wrangler 4.118.0 and an official Sandbox image digest. The checked-in Wrangler configuration names only the disposable campaign Worker, R2 bucket and Artifacts repository. It is not a shared production deployment configuration. Install with `npm ci`; run `npm test`, `npm run typecheck`, then Wrangler's dry-run build. Create the snapshot bucket before deployment. Provision `CONTROL_SECRET`, `CF_TOKEN`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` through encrypted Worker secrets, never through tracked vars or a committed dotenv file. Use a dedicated random control key and least-privilege account/R2 credentials for production; the campaign test used the existing authorized account credentials.

Cloudflare's standard Workers Builds is the separate deployment provider for Worker repositories. An operator must first configure a supported Artifacts Builds connection and persistent deployment-scoped build token. The campaign has not invented an undocumented connection-provider enum, substituted short-lived OAuth for a deploy token or silently enabled that service. C14's deployment interface must remain unavailable until a verified connection is supplied. The integration contract stores Worker tag, production/preview trigger IDs, exact SHA, external build UUID, timestamps and verified preview/deployment URLs, without copying the full provider state.

Sources: [Artifacts CI guide](https://developers.cloudflare.com/artifacts/guides/build-and-deploy-on-push/), [official CI SDK](https://github.com/cloudflare/ci), [Artifacts Builds integration](https://developers.cloudflare.com/workers/ci-cd/builds/git-integration/artifacts-integration/), [Builds API](https://developers.cloudflare.com/workers/ci-cd/builds/api-reference/). Provider setup and live Builds deployment remain a separately recorded limitation, not a certified success.
